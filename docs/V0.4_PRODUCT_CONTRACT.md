# JobTrack v0.4 product and normalization contract

Status: implementation contract for the faceted pipeline, profile normalization,
and read-only design-system release.

## Collection facets

Every collection view exposes the facets supported by its normalized records:

- company identity;
- one or more canonical general tags;
- canonical role type;
- canonical seniority level;
- domain status/phase;
- bounded free-text search where useful.

Facets use exact IDs or stable slugs. They never use fuzzy title matching or
`LIKE` against tags. Multiple tag values use explicit AND semantics. Query
parsing and option rendering are shared so invalid, duplicate, or oversized
parameters fail closed or are ignored consistently without changing the store.

Specialized taxonomies remain separate from general tags:

```text
role_types       -> opening_role_types
seniority_levels -> opening_seniority_levels
skills           -> profile/project/posting requirement relations

tag_namespaces -> tags -> explicit entity-specific tag joins
```

Application and opportunity facets traverse their normalized opening. A
discovery proposal may expose role/seniority only when an immutable extracted
projection or explicit classification exists; the web layer does not infer a
classification from arbitrary JSON or title substrings.

## Unified pipeline home

The home page is one table with a stable composite identity:

```text
(application, application_id)
(opportunity, opportunity_id)
```

It includes every application, including pre-submission prospects, and only
opportunities that have not already been promoted or linked to an application.
Pipeline phase and outcome remain distinct:

- prospective / researching / ready / submitted / interviewing / offer;
- accepted / rejected / withdrawn / closed where supported by evidence.

Accepted is derived from an accepted offer, not overloaded into the legacy
application status. Rows expose type, company, role, facets, latest activity,
profile-information gap signal, and source/provenance summary.

## Requested profile information

A posting, form, recruiter, or application may ask for information that the
profile does not currently establish. This is represented as evidence plus an
assessment, never as a bare boolean.

```text
information field definition
  -> application or opportunity request (prompt, source, requiredness, evidence)
       -> append-only assessment
            unassessed | available | confirmed_missing |
            needs_review | not_applicable
```

Absence alone remains `unassessed`. An assessment may cite the profile entry or
fact that resolves the request. A derived current-state view supplies open-gap
counts/signals for the home and collection pages. Application and opportunity
targets use separate FK-backed tables rather than a polymorphic entity ID.

## Profile normalization

Existing source bytes and structured detail tables remain intact. v0.4 adds
canonical, FK-backed vocabularies and explicit relations for:

- profile entry kind/section and confidence;
- general tags with namespace, lifecycle, sensitivity, and source metadata;
- skill/proficiency and project-stack links to canonical skills;
- exact organization/company links where identity is established;
- other genuinely enumerable kinds (link, credential, recognition,
  publication, language proficiency, work arrangement, authorization).

Compatibility JSON/free-text fields remain during the additive release and
writers dual-write. Migration backfills only exact values, never fuzzy-merges.
Unknown values remain preserved and reviewable.

## Profile information architecture

Stories are part of the profile corpus, not a peer top-level product area. The
profile page provides accessible anchor/tab-index navigation for every section,
including stories. Story detail retains its permission-aware view and raw
narration remains excluded.

Sensitive contact, reference, compensation/work-authorization, and EEO data
never enter collection facets or the unified pipeline model. Sensitive profile
sections are clearly marked and visually collapsed by default. Tailnet ACLs
remain the web UI authorization boundary.

## Shared read-only design system

All pages use one server-rendered component vocabulary:

- page shell, masthead, primary navigation, and breadcrumb;
- filter panel, select/input controls, active-facet chips, and result count;
- table/card surfaces, badges, metadata lists, empty states, and notices;
- consistent typography, spacing, color tokens, focus states, breakpoints, and
  light/dark treatment.

The implementation has no client JavaScript requirement. Filter forms are GET
only; Content Security Policy permits same-origin forms while every non-GET/HEAD
request still returns 405. The database mount and server remain read-only.

## Verification contract

- Fresh and copied-live migrations replay idempotently.
- Legacy application, opportunity, snapshot, observation, profile, and story
  bytes remain unchanged.
- All FK vocabularies reject invalid values and entity mismatches.
- Every collection facet has positive, composability, invalid-input, and
  cross-entity isolation tests.
- Unified home excludes promoted-opportunity duplicates and derives accepted
  state from offer evidence.
- Gap assessments are append-only, optimistic/idempotent, and never infer
  missing from absence.
- Profile tabs/anchors, sensitive-section treatment, responsive design, CSP,
  read-only methods, and security headers are exercised in browser/server tests.
