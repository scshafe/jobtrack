# JobTrack v0.6 strategy, communication-style, and LaTeX contract

Status: implementation contract for the application strategy control plane,
recipient-aware email drafting, and submission-ready LaTeX documents.

## Product outcome

JobTrack v0.6 adds one durable application-level control plane over the existing
specialized workflows. A frontier-capable external coordinator owns application
strategy and reconciliation. It may route bounded research, analysis, drafting,
and extraction tasks to less expensive workers under a reviewed policy, but those
workers return strict proposals only.

JobTrack remains a local store, direct-write CLI, and read-only web application.
It does not become a chat server, model host, generic tool runner, browser agent,
mail sender, or application submitter.

```text
bounded JobTrack context + exact source digest
                    |
                    v
       external frontier coordinator
                    |
          strict strategy proposal
                    v
       review -> explicit selection
                    |
          policy-derived work queue
                    |
    bounded auxiliary model or deterministic worker
                    |
           strict result proposal
                    v
 frontier/human review -> existing domain workflow
```

The release also makes resume and cover-letter revisions complete LaTeX
documents. A fixed, networkless renderer compiles them to immutable PDFs. Human
review pins the exact rendered PDF, and package/submission integrity covers both
the source and deliverable bytes.

## Non-negotiable boundaries

- The CLI remains the only JobTrack writer. The web process remains GET/HEAD-only.
- JobTrack never stores provider credentials or invokes a model API.
- Strategy work requests contain no executable, shell command, arbitrary tool,
  browser action, mail mutation, form-fill, upload, send, or submit instruction.
- A strategy result never substitutes for the target domain's own review/apply
  gate. It must be imported through the existing research, assessment, email,
  material, or interview-preparation workflow.
- Email content and job-posting content remain untrusted inert evidence.
- Recipient adaptation describes observable communication register. It never
  infers protected traits, personality, psychology, dialect, or identity.
- Outgoing prose remains Cole's voice. It may accommodate formality, warmth,
  energy, directness, and brevity, but never copies distinctive recipient phrases,
  errors, slang, signatures, or mannerisms.
- A reviewed email draft still has `autoSendEligible=false` and grants no send
  authority.
- TeX never runs on the host or in the web image. Rendering receives no JobTrack
  store, credentials, browser data, Docker socket, network, or arbitrary mounts.
- Existing application, opportunity, profile, email, form, material, package,
  and lifecycle records are never rewritten or inferred into new v0.6 history.

## Application strategy control plane

### Strategy context

Strategy generation uses the same two-pass pattern as application materials.

The first read returns a bounded metadata catalog. It may describe available
application artifacts, posting snapshots, profile entries, approved story uses,
interviews, email facts/proposals, material readiness, and prior strategy history,
but it does not silently select source prose.

The second read names exact source IDs. It may include only same-application,
purpose-eligible records and returns a canonical `sourceStateSha256`. The source
manifest pins at least:

- application ID, lock version, status, and workflow stage;
- normalized company, opening, posting occurrences, and posting snapshots;
- selected posting/research artifacts and attachment-byte digests;
- current assessment and assessment-review state;
- form-state and application-material readiness digests;
- interview schedule versions and selected preparation digests;
- selected sanitized email facts/correlation/proposal digests;
- previous selected strategy revision;
- explicitly selected profile entries and approved story uses.

Raw MIME, mailbox archives, protected form answers, Equal Employment Opportunity
(EEO) data, credentials, attachment paths, raw story captures, and unrelated
profile prose are excluded. Every plan import recomputes the selected context in
the write transaction and rejects stale input.

### Plans and work graph

An application strategy is an immutable, versioned plan with a bounded objective,
phase, positioning thesis, evidence-backed strengths and gaps, risks,
assumptions, reassessment conditions, and a directed acyclic graph of work items.

Each work item has:

- a stable plan-scoped key;
- one closed capability;
- a goal and bounded acceptance criteria;
- priority and risk class;
- one strict output kind;
- dependencies within the same plan;
- an explicit review requirement.

Plan creation, review, and selection are separate append-only actions. A plan must
declare a frontier coordinator. A new plan never silently replaces the selected
one. Only an approved revision can become current, using an expected-current
guard.

### Model routing

Routing is provider-independent. JobTrack stores logical route aliases and actual
execution receipts, not credentials or provider invocation details.

The closed model classes are ordered:

```text
deterministic < economy < strong < frontier
```

Initial capabilities and minimum defaults are:

| Capability | Default class | Escalation |
| --- | --- | --- |
| application strategy / reconciliation | frontier | human review |
| company research / job-post analysis | strong | frontier |
| application-material / email drafting | strong | frontier |
| interview preparation | strong | frontier |
| email signal / tone extraction | economy | strong, then frontier |
| LaTeX rendering | deterministic | operator failure review |

The reviewed routing policy defines route aliases, minimum class, escalation
class, confidence floor, attempt limit, and token/cost/time ceilings. Ambiguous,
sensitive, high-value, low-confidence, invalid-contract, or repeatedly failed
work escalates. An over-budget result is retained for audit but cannot be accepted
without the policy's explicit override path.

JobTrack can validate the declared class, policy, and receipt. It cannot prove
which commercial model actually ran without a future signed-receipt protocol.

### Work requests and results

Issuing work pins the selected plan, work item, routing-policy revision, selected
source state, route alias, minimum class, attempt number, and budgets. It does not
execute the task.

Results bind the exact request digest and record worker/model/version provenance,
confidence, duration, token/cost receipt, budget outcome, strict output JSON, and
output digest. Result events are append-only: recorded, accepted, rejected,
escalated, blocked, or superseded.

Accepted results are proposals. Their effects still use the appropriate domain
path:

- research -> `add-research`;
- job analysis -> assessment creation and assessment review;
- email -> reply-draft proposal and review;
- documents -> material draft, render, review, and selection;
- interview preparation -> analysis creation, review, and selection.

For proposal-producing work, a typed binding is required before the work item is
complete. It records the exact same-application domain row after that domain
operation succeeds. Pure analysis may complete on acceptance. Strategy acceptance
itself never writes the target domain state.

Because a successful domain operation legitimately changes the application source
state, binding requires an explicit source checkpoint. The caller supplies the
current source-state digest, actor, and reason; JobTrack verifies that the drift is
the expected target-kind change, records old and new digests append-only, and
supersedes work requests derived from the previous state. Unrelated drift fails
closed and requires a fresh strategy context/reconciliation.

## Recipient-aware email communication

### Separate observation, recipient profile, sender voice, and tone

The email workflow has four deliberately separate concepts:

1. A message observation records bounded surface features from one sanitized
   inbound message.
2. A recipient style profile aggregates reviewed eligible observations for one
   thread or one exactly bound company contact.
3. A writing-voice revision records Cole-owned, explicitly approved sender style.
4. A tone decision chooses a bounded adaptation for one reply purpose and source
   state.

This separation prevents a recipient's prose from entering Cole's writing-voice
corpus and prevents one cheerful or terse message from becoming a durable claim
about a person.

### Message observations

An observation binds the exact provider/account/message/thread reference and the
existing facts/content digests. It may record only deterministic surface signals
and closed dimensions:

- length band, greeting type, closing type, exclamation band, emoji presence,
  and contraction use;
- formality: casual, neutral, formal;
- warmth: reserved, neutral, warm;
- energy: restrained, neutral, upbeat;
- directness: direct, balanced, contextual;
- verbosity: terse, concise, moderate;
- one bounded overall extraction confidence plus model/policy provenance.

Evidence refers to indexes in the existing bounded facts evidence array. It does
not copy arbitrary message prose. Metadata-only, automated/shared, medium/high
security-risk, prompt-injected, incomplete, or source-review-required messages
are ineligible for contact aggregation.

Fields describing personality, mood, protected traits, psychology, demographics,
dialect, accent, native language, or identity are invalid contract fields.

### Contacts and aggregation

Provider/account/thread identity becomes a first-class projection without
rewriting append-only message rows. `company_contacts` remains the canonical
person/contact table. Email addresses bind to contacts only through reviewed,
append-only bind/unbind events; a `From` header never creates a person
automatically.

A thread profile may use one eligible message but remains low confidence and may
move at most one band from Cole's baseline. A contact profile requires at least
three eligible human-authored messages across at least two threads. Aggregation
uses no more than the latest eight eligible messages with equal weighting;
conflicts collapse toward neutral professional. Profiles are immutable,
reviewed, explicitly selected, and visibly stale after newer conflicting evidence
or the policy horizon.

### Cole writing voices

A writing voice is a stable named identity such as `warm-professional` or
`concise-professional`. Its immutable revisions contain closed dimensions,
greeting/closing preferences, punctuation constraints, and bounded delivery rules.
They may carry up to eight opaque sample digests under a Cole ownership attestation,
but v0.6 does not store or independently verify a managed prose corpus. Recipient
text, employer text, model-invented examples, and unreviewed mailbox content remain
forbidden inputs. Voice revision creation, review, and selection are separate.

### Tone decisions and reply proposals

A tone decision binds one imported message/thread, reply purpose, optional
application/contact, current approved recipient profile, selected approved Cole
voice, routing/model provenance, and the exact communication source-state digest.

Tone policy may adapt register within these limits:

- at most one exclamation mark when warmth/energy evidence warrants it;
- emoji remains off unless an explicitly approved future policy permits
  reciprocal use;
- sensitive, legal, compensation, offer, rejection, or ambiguity contexts force
  conservative professional constraints;
- slang, typos, dialect, catchphrases, distinctive phrases, and signature mimicry
  remain forbidden.

A styled reply proposal binds the exact tone decision/profile/voice digests,
keeps the v1 body/recipient/content safeguards, requires human review for
model-authored prose, and remains permanently no-send.

## LaTeX resume and cover-letter workflow

### Source contract

New resume and cover-letter revisions are complete, self-contained LaTeX
documents under `jobtrack-latex-document-v1`. Form answers remain plain text.
Callers cannot claim a different source format.

The selected generation context advertises:

```json
{
  "sourceFormat": "latex",
  "contractVersion": "jobtrack-latex-document-v1",
  "completeDocument": true,
  "selfContained": true,
  "outputFormat": "pdf",
  "externalInputsAllowed": false
}
```

The LaTeX source is immutable evidence-bound material content. Regex filtering is
not treated as a compiler or security boundary.

### Rendering boundary

Rendering is a fixed deterministic worker. The host CLI invokes Docker with an
argument array and a pinned local renderer profile. It never accepts a caller
executable, image, command, mount, output path, or pull policy.

The renderer runs with:

- `--pull=never`, `--network=none`, and a read-only root filesystem;
- all capabilities dropped and `no-new-privileges`;
- fixed CPU, memory, process, wall-clock, and output limits;
- the host UID/GID;
- a private read-only input directory and separate empty output directory only;
- no JobTrack store, home directory, credential, browser, Docker socket, or other
  host mount;
- shell escape disabled and a fixed offline TeX package set.

The host verifies the exact expected regular output files, rejects symlinks and
extra outputs, checks PDF magic/structure/page count/selectable text and bounded
page geometry, enforces a byte limit, hashes the result, copies it collision-safely
into managed private attachments, and cleans staging on every failure. The fixed
`jobtrack-pdf-active-content.v1` scan rejects scripts, launch actions, embedded
files, forms/XFA, remote go-to/submit/import actions, rich media, unsafe URI schemes,
and other active content while permitting structurally verified internal document
destinations and `http`, `https`, `mailto`, or `tel` links. Its policy and byte-bound
scan digest are persisted with the render. Compiler logs may echo private source
and are never stored in public projections.

### Review, readiness, package, and submission

Each render binds the exact material revision/source hash, renderer profile and
image digest, renderer version, package bundle digest, PDF digest/size/page count,
text-extraction digest, actor, and idempotent intent.

An approved resume or cover-letter review must pin one exact successful render.
A later render does not supersede that reviewed PDF. Form-answer reviews cannot
pin document renders.

Readiness requires current selected approved LaTeX revisions and their exact
reviewed, integrity-valid PDFs. Package creation binds both render IDs and PDF
digests in addition to all v0.5 form, assessment, answer, information, profile,
and attachment state. Package integrity and manual-submission recording rehash
both PDFs. Missing, stale, modified, cross-application, or unreviewed renders fail
closed.

The package manifest names the exact resume and cover-letter deliverables rather
than embedding raw TeX as if it were the submission document. The PDFs remain
separate because applicant tracking systems generally request separate uploads.

The web UI shows source format, render/review state, digest, byte/page count, and
package binding only. It does not serve PDFs, reveal attachment paths, or show
compiler logs in this release.

## CLI surface

The intended v0.6 commands are:

```text
jobtrack strategy policy import|review|select|show
jobtrack strategy context
jobtrack strategy plan import|review|select|show
jobtrack strategy queue|status
jobtrack strategy work issue|record|review|bind

jobtrack email import-demeanor
jobtrack email communication-context
jobtrack email propose-style-profile|review-style-profile|select-style-profile
jobtrack email voice create|revise|review|select|show
jobtrack email propose-tone
jobtrack email propose-reply|review-reply

jobtrack application-material context|draft
jobtrack application-material render
jobtrack application-material review|select|readiness
jobtrack build-package
jobtrack application-material record-submission
```

The exact action-level flag schema remains closed. Unknown, duplicate, irrelevant,
or malformed flags fail before database, filesystem, renderer, or external
interaction.

## Read-only web projections

The application workspace adds:

- selected strategy freshness, phase, objective, risks, active/blocked work,
  route class, budget state, and review state;
- collapsed communication-style metadata for linked application threads/contacts,
  without raw evidence, bodies, exact private addresses, samples, or draft prose;
- LaTeX source contract, render status, reviewed PDF metadata, and package binding.

No-plan/no-observation/no-render states remain explicit. Cross-application IDs
return `404`. All user/external/model strings are escaped. The server retains its
read-only database, loopback binding, no-store headers, Content Security Policy,
non-root user, read-only filesystem, dropped capabilities, and lack of Docker or
mail credentials.

## Migration and compatibility

The schema-10 to schema-11 release is additive and transactional. Its coordinated
migrations are:

```text
2026071801 application_strategy_control_plane
2026071802 recipient_aware_email_communication_style
2026071803 latex_application_material_rendering
```

Migration must replay idempotently and detect ledger name/version conflicts.
Closed vocabularies and safe projections may be seeded. It must not invent plans,
routing-policy approvals, work requests/results, message observations, contact
bindings, style profiles, voice revisions/sample attestations, tone decisions, LaTeX renders,
render-bound reviews, package bindings, or submission facts.

Legacy material rows retain an explicit legacy source contract. New managed
resume/cover-letter revisions use the LaTeX contract. Existing historical
packages remain readable and are not rewritten.

Copied-live rehearsal must prove every inherited table and row projection is
byte-equivalent before and after migration, with SQLite integrity and foreign-key
checks clean. A verified schema-10 backup and v0.5 web image remain the rollback
pair.

## Verification contract

The release is not complete until all of these gates pass:

- strict contract tests reject unknown fields, executable/tool payloads,
  low-tier coordinators, cycles, sensitive-trait/personality inference,
  recipient phrase samples, stale digests, and mismatched recipients;
- strategy tests cover plan/review/selection separation, routing floors, budgets,
  escalation, result receipts, append-only history, idempotency, same-application
  scope, and domain-gate preservation;
- email tests cover account-scoped thread identity, reviewed contact binding,
  eligibility, deterministic aggregation, neutral conflict behavior, voice ownership
  attestations, high-risk tone overrides, no mimicry, and permanent no-send;
- LaTeX tests cover source locks, renderer arguments/isolation, compiler failure,
  timeout, oversize/extra/symlink output, private collision-safe copies,
  render-bound approval, PDF tamper detection, package/submission binding, and
  public redaction;
- normal tests use deterministic injected renderer fixtures and require no Docker;
- an opt-in real-container test compiles representative resume and cover-letter
  fixtures with the exact release renderer image;
- fresh and copied-live migrations replay twice with no inherited drift;
- the full Node test suite, syntax, diff, dependency audit, Docker Compose,
  container isolation, read-only web, local route, and Tailnet route gates pass;
- independent reviewers clear accepted high/medium findings before release;
- no model runner, email sender, form submitter, unrestricted network worker,
  compiler, or Docker socket is present in the deployed web container.

## Follow-ups deliberately outside v0.6

- Signed model execution receipts and provider attestation.
- Autonomous model execution from JobTrack itself.
- Email send, label, archive, delete, attachment, CC, or BCC authority.
- Browser form filling, upload, advancement, or final submission.
- Inline PDF serving or a PDF download route in the web UI.
- Structured resume abstract syntax trees and mutable template inheritance.
- Company-wide communication-style inference.
- Recurring discovery scheduling.
