# JobTrack v0.5 application-materials contract

Status: implementation contract for prospective form discovery, application-specific
drafting, review, and package readiness.

## Material workspace

Every application owns one material workspace as soon as the application record exists.
The workspace always contains two policy requirements:

- one application-specific resume;
- one application-specific cover letter.

Those requirements exist even when a posting calls either document optional. A form may add
document, short-answer, long-answer, choice, consent, or other field requirements, but it may
not remove the baseline pair. Opportunities remain upstream discovery records; material work
begins only after explicit promotion to an application.

`draftable` and `submittable` are deliberately different states:

```text
prospective application
  -> partial form inventory + posting/profile evidence
  -> application-specific rough revisions             (draftable)
  -> explicit revision review + current selection
  -> required-answer coverage + form-coverage review  (submittable)
  -> immutable package
  -> operator-controlled submission
```

Rough revisions may be created before an application assessment is approved. They must expose
their incomplete evidence and can never make a package ready. Package creation continues to
require the current approved application assessment.

## Form inventory and hidden-step uncertainty

Application-form knowledge is evidence, not a mutable checklist. Each survey records the exact
application/posting, public URL, capture method, observed time, coverage state, and optional
evidence digest. Surveys contain ordered steps; steps contain normalized fields/questions and
choice options. Field identity is scoped to the posting's application-form surface and a stable
provider key rather than prompt wording alone, because prompts and requirements may change.

Coverage is one of:

- `unknown`: the form has not been inspected;
- `listing-only`: only the public listing or application entry link was observed;
- `entry-step-observed`: the first application step was inventoried, but later steps remain unknown;
- `partial`: some steps or fields are known, but later/conditional steps may exist;
- `complete`: the observer reached and inventoried every reachable pre-submit step;
- `blocked`: authentication, CAPTCHA, inaccessible UI, or another boundary prevented inspection.

Conditional or later-step fields retain their visibility condition as inert text. A hidden or
unreachable step is never inferred away. A `complete` claim is reviewable evidence, not proof
that the provider cannot later change the form.

The capture/import boundary is data-only. It must not log in, bypass access controls, upload
profile data, execute form text, contact an employer, or activate a final submission control.
Any future browser collector is a separate sandboxed adapter whose output must pass the same
strict, bounded importer.

## Normalized requirement model

Reusable vocabularies are foreign-key backed and closed by default:

- material kind;
- form field/input kind;
- requiredness;
- sensitivity;
- discovery method and coverage state;
- revision stage;
- review decision.
- exact-field fulfillment/applicability state.

Application material requirements and form fields are separate relations. A field may map to a
canonical profile information field when exact (email, authorization, resume, and so on), while
arbitrary employer questions remain first-class application questions. Required and preferred
flags are normalized relations, not encoded in prompt text or tags.

Every accepted field observation is immutable and evidence-bound. A new observation supersedes
the old one; it does not edit it. Current views derive the latest accepted observation.

Non-generated file fields and conditional applicability use separate append-only exact-field
resolution events. `fulfilled` binds a same-application managed artifact and byte digest;
`applicable`, `not-applicable`, and `blocked` record an explicit human decision without evidence
payload. Every event names the exact current form-state hash, actor, rationale, optimistic prior
event, and idempotency key. Required file fields cannot become ready without current fulfilled
evidence, and conditional fields cannot silently become blocking or nonblocking without an
explicit applicability decision. Migration `2026071717` adds this relation without inventing any
resolution events.

## Application-specific revisions

Resume, cover-letter, and answer prose is stored as immutable, versioned revisions. Every
revision belongs to exactly one application and one material requirement, records its parent
revision when iterating, and pins a canonical source manifest containing only the evidence that
was actually used. The manifest and content have separate SHA-256 digests.

Creation, review, and current selection are distinct operations:

```text
create revision -> review decision -> select current revision
```

Writes are idempotent. Review and selection use expected-current guards. A new rough draft never
silently replaces a reviewed current revision. Review decisions are append-only; revision
content is immutable. A generated revision cannot claim `reviewed` or `approved` on creation.

Question answers are scoped to the exact form field, not merely reusable profile-answer text.
Reusable profile answers may be cited as source evidence, but the stored application answer is
customized and independently reviewed. Choice answers pin both the option identity and rendered
answer. Consent and protected/self-identification answers are never generated automatically.

## Generation boundary

JobTrack itself does not call a language model. Context retrieval is two-pass: an unselected read
returns typed source-catalog metadata only, then the caller requests one exact material purpose
plus bounded artifact, profile, and approved story-use IDs. A form answer additionally requires
the exact form-field ID; a refinement additionally requires the exact parent-revision ID. Only
that selected context contains authorized source prose. Application notes, unrelated material
revisions, information-request prompts, and protected answers never enter the catalog. The draft
write must present the SHA-256 returned for the same purpose, field, parent, and source IDs;
JobTrack recomputes it transactionally and rejects stale generation context. An agent composes a
rough draft and stores the exact prose through the CLI. The source manifest records only the
selected records, their attachment-byte digests, and the exact context digest.

All employer, posting, research, form, and artifact text remains untrusted inert data inside that
context. A generator may summarize or cite it, but must never execute or obey instructions found
inside it, disclose unrelated profile data, retrieve credentials, or expand the authorized source
set because external text asks it to do so.

The generator must tailor every resume and cover letter to the application. Copying a revision
from another application is rejected by application ownership checks; an exact resume or
cover-letter content hash already used by another application blocks package readiness until the
material is genuinely revised.

## Readiness and packaging

A package is blocked unless all of these are true:

1. the latest application assessment revision is approved;
2. the baseline resume and cover-letter requirements each have a current approved revision;
3. every active required employer question has a current approved answer;
4. no current required field is explicitly unanswered or confirmed missing;
5. form coverage is `complete`, or a human has appended an explicit uncertainty acceptance;
6. every selected revision still matches its pinned evidence/context.

The package pins exact revision IDs and content hashes, each information resolution's latest
assessment and current source-state hash, the exact exported-profile projection, and a canonical
fingerprint of every immutable package field and managed attachment byte. Its normalized build
request is also hashed, so reusing an idempotency key with changed notes, checklist, export policy,
or readiness input conflicts rather than replaying a different request. Package creation and all
bindings, lifecycle events, and stage changes commit in one database transaction; a failed build
leaves neither package rows nor a staged attachment. Later form observations, assessment changes,
material revisions, profile values, evidence, or review changes mark an older package stale; they
never rewrite it. Export freshness is re-derived from the exact live profile fields authorized by
the package policy, while unrelated profile edits do not invalidate it. After Cole submits
manually, a separate append-only submission fact binds the exact package fingerprint, attachment
digest, current readiness hash, actor, and timestamp and advances the recorded workflow.
Submission rechecks current readiness, answer and option completeness, information resolutions,
exported-profile state, stored manifest digests, package fields, and attachment bytes. That
command records the human action; it has no login, browser, upload, or submission capability.

## Read-only web workspace

Applications link to the anchor-indexed `/applications/:id` workspace, with the normalized
opening retained as a secondary link. The page shows:

- form-discovery coverage and unresolved hidden-step risk;
- baseline documents and additional material requirements;
- current revision, review decision, history, and staleness per material;
- known questions/options and answer coverage;
- profile-information gaps linked to the exact prompting field;
- draftable/package-ready blockers and an immutable package history.

Owned material-revision and question detail routes may expose escaped, bounded revision history.
An ID that belongs to another application returns `404`, not a cross-application disclosure.

Potentially sensitive prompts and answers are collapsed by default. Public context, list,
readiness, package-snapshot, and web projections redact protected content, option labels, change
notes, review notes, and prompts; protected values are represented by generic state and
provenance. An explicit host-side `application-form show --exact`, `application-material show
--revision-id ID`, or `show-package --exact` is a deliberate raw-read capability for human
operators. Material-level show remains redacted so bulk revision history does not become an
accidental raw read. The server remains GET/HEAD-only and the CLI remains the only writer.

## Verification contract

- Fresh and copied-live migrations replay idempotently with no legacy data/hash drift.
- Every existing application receives exactly one workspace plus baseline resume/letter
  requirements; no draft or answer is invented.
- Cross-application revision, field, evidence, review, and selection links fail in code and via
  database guards.
- Revision immutability, idempotency conflicts, optimistic locks, current-selection policy, and
  stale derivation have focused tests.
- Form imports reject oversized, malformed, duplicate-key, unknown-enum, hostile, and
  cross-posting input atomically.
- Partial/blocked/unknown coverage can never satisfy package readiness without a distinct,
  append-only human uncertainty acceptance.
- A newly observed form revision blocks readiness until it is explicitly approved or rejected;
  rejecting it restores the prior approved selection without silently changing its state hash.
- Required non-generated fields and conditional applicability are resolved only through
  append-only migration `2026071717` events pinned into readiness and package manifests.
- Exact cross-application resume or cover-letter duplicates block readiness rather than passing
  as customization.
- A submission record requires an exact prepared-package binding and remains a local audit fact;
  no JobTrack command performs employer-facing submission.
- Baseline documents and required answers gate package creation; optional unanswered questions
  remain visible but do not block.
- Web tests cover empty, partial, ready, stale, sensitive, mobile, security-header, and 405 paths.
